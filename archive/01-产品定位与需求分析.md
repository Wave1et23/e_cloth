| 项目 | 内容 |
| --- | --- |

## 1. 产品定义

### 1.1 一句话定位

> **衣橱镜像是一个连接实体衣柜与数字世界的智能衣物管理系统。**
>
> 用户通过 AI 在 3 秒内完成一件衣物的建档，系统为每件衣物生成唯一数字标签；标签打印后贴在现实衣架上，此后每次穿、洗、收、卖，**用手机相机扫一下**（手机系统相机自带扫码，无需安装任何扫码器），即可完成状态更新。随着真实数据积累，系统能告诉用户：这件衣服穿了多少次、单次穿着成本是多少、衣柜里有多少钱在闲置。

### 1.2 三句话版本

1. **对用户**：不用记、不用敲，衣架上的一个二维码，就能让线上衣柜知道这件衣服今天被你穿了。
2. **对产品**：我们卖的不是「记录工具」，而是「让用户第一次看清自己真实衣柜」的能力。
3. **对评委**：确定性任务（二维码编码、解码）用系统能力与传统算法，语义任务（衣物属性识别）用多模态模型，所有 AI 结果经用户确认后才落库 —— 这是一个有工程判断的 AI 应用，而不是把 AI 硬塞进 CRUD。

### 1.3 产品类比（说给不懂的人听）

- 像给衣柜做了一次 **「图书编目 + 借阅登记」**：每件衣服有了索书号和借阅卡。
- 像给衣服装了一个 **「行车记录仪」**：不预测未来，只如实记下已经发生的事。
- 像给衣柜做了 **「体检报告」**：不催你买新的，而是告诉你旧的有多值。

### 1.4 它不是什么（写下来防止团队跑偏）

| 容易滑向的错误定位 | 为什么不能这么做 |
| --- | --- |
| 又一个「线上衣柜 + AI 搭配」App | 市面已有大量同质产品，属于红海，评委会问「凭什么是你」 |
| AI 穿搭助手 / AI 造型师 | 别人的主赛道，我们的数据优势不在这里，且效果难验证 |
| 衣物二手交易平台 | 是下游渠道，不是本文定义的产品，最多作为状态出口之一 |
| 一个精致的衣物 CRUD 后台 | 没有差异化，也没有解决「数据从哪来」这个死穴 |
| 「用了 AI 所以很先进」的演示项目 | 技术叙事错误，把扫码说成 AI 是减分项 |
| **功能很多但每个都半成品** | **v2.0 特别强调：4 周内「5 个功能全通」远胜「15 个功能各通一半」** |

**关键判断：我们做的不是 Clothes CRUD System，而是 Physical Garment Lifecycle Management System（实体衣物生命周期管理系统）。**

## 2. 要解决的实际问题

### 2.1 问题的起点：数字衣柜的「最后一公里」断裂

现有数字衣柜产品（Ovylo、Dayclo、Lookora、Closet DJ、Wheron 等）普遍已经做到：拍照录入、按颜色/季节/类别分类、搭配推荐、穿着次数统计、Cost Per Wear、洗衣状态、天气结合推荐。**功能层面并不缺。**

真正缺的是这条链的**后半段**：

```
用户买了衣服 → 拍照录入线上衣柜 → ❓ 之后呢？
                                    ↑
                          这里开始断裂：
                          线上系统无法感知
                          线下衣服发生了什么
```

结果是：
- 用户第一次很兴奋地录入 30 件衣服，之后新买的懒得录，旧的懒得改；
- 穿着次数靠用户「记得住就去点一下」，两周后数据归零；
- 衣柜 App 变成一个「僵尸数据库」——里面存的是三个月前的世界。

**所以我们真正要解决的问题不是「怎么记录衣服」，而是「凭什么让记录这件事自己发生」。**

### 2.2 五个可被真实感知的问题

#### P1｜记录成本过高，数字衣柜必然半途而废

- **场景**：晚上 11 点，用户想起来白天穿了白衬衫和黑裤子，打开 App → 搜索「白衬衫」→ 找到记录 → 修改状态 → 再重复一遍黑裤子。
- **表现**：单次记录 30–90 秒，一天两件就是 3 分钟；一周后彻底放弃。
- **现有方案为何失败**：所有产品都把「打开 App → 定位到那件衣服」的成本留给了用户，而这一步恰好是最贵的。
- **我们的解法**：**扫码即操作**。衣服就在手边（出门拿、回家挂、送洗时），手机相机扫衣架上的二维码 → 直接落在这件衣服的快捷面板 → 一键「今天穿了」。**从「搜索并定位」变成「对准并点击」，操作步骤从 5 步降到 2 步。**
- **为什么这是真问题**：这不是「体验优化」，这是决定产品能否活过第二周的分水岭。

#### P2｜记忆不可靠：忘了有什么、在哪、洗没洗

- **场景**：早上找一件灰色卫衣，翻箱倒柜；或者临出门才发现那件外套上週送洗了还没取；换季收纳后第二年忘了自己有条亚麻裤。
- **表现**：每天 1 分钟级别的无意义搜索，换季时大量「惊喜发现」和「重复购买」。
- **现有方案为何失败**：纯数字列表无法回答「物理位置」和「当前物理状态」，因为没人有动力手动维护。
- **我们的解法**：把**物理状态**做成扫码的一等公民 —— `在柜 / 穿着中 / 待洗 / 已收纳 / 已退出`，扫一次码就更新一次，状态始终跟着现实走。

#### P3｜数据盲区：不知道自己的衣柜有多「低效」

- **场景**：用户觉得「我衣服好像挺多的」，但说不出：去年买了 31 件里有多少件穿了不到 3 次；黑色长裤不知不觉买了 5 条。
- **表现**：重复购买、冲动消费、衣柜膨胀但「没衣服穿」的经典矛盾。
- **现有方案为何失败**：多数产品有 Cost Per Wear 这个数字，但**输入数据是坏的**（穿着次数长期为 0 或乱填），所以算出来的数字没人信。
- **我们的解法（v2.0 范围）**：MVP 只交付**三个能站住的数字**：
  1. **本月穿着次数**（全衣柜汇总）
  2. **在柜件数**
  3. **单件 Cost Per Wear**（显示在衣物卡片上）

  「闲置清单」「重复购买识别」列为**加分项，四周内不做** —— 它们需要足够的历史数据才好看，而 MVP 阶段根本攒不出 90 天数据。
- **这恰好是产品理念**：帮助用户了解自己的消费与衣柜，而**不是鼓励买更多衣服**。

#### P4｜护理知识缺失，好衣服被洗坏

- **场景**：一件羊毛衫，用户凭感觉丢进洗衣机，缩水报废；或真丝衬衫用了漂白剂。
- **表现**：单件损失几百到几千元，且用户不理解错在哪。
- **现有方案为何失败**：水洗标是一堆看不懂的符号；查攻略要跳出去。LaundryMax 等产品已验证「拍标识别 + 护理建议」这一使用场景成立。
- **我们的解法（v2.0 范围调整）**：**从产品功能降级为离线实验。**
  - 写脚本跑 8–10 张真实水洗标，记录 V1 → V2 的 Prompt 迭代效果；
  - 结论写进 `docs/EVAL-REPORT.md`，作为「AI 能力边界探索」的材料；
  - **不做进 MVP 界面**（不做独立上传入口、不做护理提醒弹窗）。
  - **理由**：它对「扫码闭环」这个核心假设没有贡献，但对「证明 AI 迭代能力」有很高价值 —— 用 1 天做实验能拿到 90% 的叙事收益，用 3 天做产品只有额外 10%。
- **为什么原本必须和衣物识别拆开**：混在一个 Prompt 里，模型会**根据衣服外观臆测材质**（看到「白色衬衫」就写「棉」），这是幻觉。这个拆分结论本身就是最好的实验案例。

#### P5｜「做减法」这件事本身缺少工具与仪式感

- **场景**：想断舍离，但不知道从哪件开始；想卖二手，不知道哪些值得卖。
- **表现**：闲置衣服长期占空间，最终整袋丢弃，浪费且不环保。
- **现有方案为何失败**：二手平台只管交易，不管「哪些该被卖掉」这个决策。
- **我们的解法（v2.0 范围）**：MVP 只保证「出售」是扫码面板上的一个常规按钮，**让退出成为一个轻动作**，而不是一场痛苦的年度大扫除。真正的闲置分析留到数据积累之后。

### 2.3 需求分级（v2.0 修正）

| 层级 | 需求 | 对应问题 | v2.0 是否做 |
| --- | --- | --- | --- |
| **底线（不做产品不成立）** | 拍照 + AI 建档（单件 ≤ 10 秒） | P1 | ✅ 做，**核心** |
| **底线** | 扫码更新状态（穿/洗/收/卖） | P1 P2 | ✅ 做，**核心** |
| **底线** | 二维码可打印、可粘贴、**手机相机能扫开** | P1 | ✅ 做，**核心** |
| **底线** | AI 识别结果人工可确认、可修改 | P4 | ✅ 做，**核心** |
| **核心价值** | 本月穿着次数 + 在柜件数 + 单件 CPW | P3 | ✅ 做，**精简版** |
| **核心价值** | 每次状态变更留有历史记录 | P2 | ✅ 做，`events` 表 |
| **加分（有余力才做）** | 水洗标实验报告 | P4 | ⚠️ 占 1 天，不进产品 |
| **加分** | 闲置清单、重复购买提示 | P3 | ❌ 数据攒不够，不做 |
| **非本产品职责** | AI 搭配、天气、社区、二手对接、NFC、多规格标签 | — | ❌ 坚决不做 |

**一句话原则：体验的成败在「录入」和「扫码」两处，不在「推荐」和「分析」上。**

### 2.4 整个产品的核心假设（必须用真实用户验证）

> **假设 A（生死假设）**：扫码的操作成本显著低于手动记录，且用户愿意为衣柜里的每件衣服贴标签。
>
> **假设 B**：用户接受「AI 自动填表 + 我点确认」这种半自动建档方式，而不会觉得「AI 猜错了还要我改，不如自己填」。
>
> **假设 C**：用户真正在意的是「我用得值不值」这类数据洞察，而不是「今天穿什么」这类推荐。
>
> **假设 D**：用户愿意为每件衣服补录价格 —— 至少愿意为「值得计算的那部分」补录。

**验证方式（v2.0 成本下调）**：3 位同学各试用一次并录屏（第 9 周）+ 开发期与队友的日常试错。假设 A 若被推翻，产品需重新设计交互；假设 A 成立，这个方向值得继续投入。

## 3. 目标受众

### 3.1 用户筛选逻辑

```
所有有衣服的人
   │  ├── 衣物 < 30 件 → ✗ 不需要系统，记在脑子里
   │  ├── 完全不关心穿搭 → ✗ 无动机
   │  ├── 衣物 30–80 件 → ○ 边缘用户，痛点不痛
   ▼
衣物 80–200 件、有穿搭意识、有过「吃灰 / 重复买 / 忘状态」经历的人
   │  ├── 不愿付出任何学习成本 → ✗ 流失
   ▼
愿意为了长期收益，花 40 分钟完成首次建档的人  ← 这才是我们的用户
```

### 3.2 主目标用户画像

#### Persona 1｜「衣柜很大但总觉得没衣服穿」的城市白领女性（首要）

| 维度 | 描述 |
| --- | --- |
| 年龄 | 24–32 岁 |
| 城市 / 居住 | 一二线城市，租房或小户型，独立衣柜/衣帽间空间紧张 |
| 职业 | 互联网、金融、设计、媒体等，有通勤 + 社交两套场景 |
| 衣物规模 | 120–200 件（含换季收纳） |
| 消费特征 | 每季添置 5–15 件；有明确的「这件贵但值得」观念；会在电商大促冲动下单 |
| 现有习惯 | 用小红书收藏穿搭、用备忘录记干洗、衣柜按颜色/季节分区 |
| 典型痛点 | 「明明衣柜满了却说没衣服穿」；「去年买的毛衣今年才发现没穿过」；「黑色长裤买了四五条」 |
| 已尝试的方案 | 下载过 Closet App，录了 20 件就弃用 |
| 使用动机 | 不是省钱，是**「想搞清楚自己到底有多少浪费」** 和 **「不想每天早上浪费 10 分钟找衣服」** |
| 付费意愿 | 中高（愿为「衣柜管理」类工具付月费，但要求立刻见效） |
| 会被什么打动 | 看到自己的「闲置清单」和「Cost Per Wear 排行」那一刻的震撼感 |

#### Persona 2｜「效率至上、数据驱动」的技术/产品从业者男性（次要但极佳种子用户）

| 维度 | 描述 |
| --- | --- |
| 年龄 | 26–35 岁 |
| 衣物规模 | 60–120 件，以基础款为主，重复率极高 |
| 特征 | 认同「用系统替代记忆」，喜欢一切可以量化的东西；对「贴标签」这件事毫无心理障碍 |
| 典型痛点 | 早上不想决策，希望衣柜像代码库一样有索引 |
| 会被什么打动 | 手机一扫 3 秒更新状态、成本数据的可视化 |
| 产品价值 | 这类用户是**最好的 Demo 拍摄对象和口碑传播者** |

### 3.3 次目标用户

| 人群 | 真实需求 | 与主产品的关系 |
| --- | --- | --- |
| 可持续消费 / 极简主义实践者 | 减少浪费、控制购买欲、识别闲置 | 与产品理念高度契合，是最好的「价值叙事」样本 |
| 二手转卖活跃者（闲鱼重度用户） | 快速找出「该卖的衣服」并给出转卖理由 | 生命周期出口的自然使用者 |
| 宝妈 / 多口之家 | 家庭成员衣物混杂，需要区分归属 | 未来可扩展「多衣柜 / 家庭共享」，**MVP 连 Wardrobe 表都不建** |
| 衣物租赁 / 买手店 / 高端干洗店（B 端） | 多件衣物的状态与流转追踪 | 远期商业化方向，MVP 不做 |

### 3.4 明确不服务的人群

- 衣物 < 30 件、靠记忆即可管理的人 —— 产品对他是负担。
- 完全没有穿搭意识、不在乎衣柜效率的人 —— 无动机，教育成本过高。
- 只想看 AI 推荐搭配、不愿投入任何记录的人 —— 他的需求属于「AI 造型 App」。
- 期待我们替他把衣服「全自动」管起来的人 —— 我们需要用户做最少但必要的动作（贴标签、确认 AI 结果）。

### 3.5 使用场景地图

| 时机 | 地点 | 用户动作 | 产品价值 |
| --- | --- | --- | --- |
| 首次使用（1 次，约 30–60 分钟） | 家里衣柜前 | 批量拍照 → AI 预填 → 确认入柜 → 打印标签 → 贴衣架 | 建档 |
| 每件新衣服入柜（高频） | 家里 | 拍一张 → 确认 → 打标签 | 不让数据断层 |
| **早上出门（每天）** | **衣柜前 / 玄关** | **手机相机扫衣架 → 点「穿了」** | **3 秒记录** |
| 换下 / 送洗（每周） | 家里 | 扫衣架 → 「洗了 / 送干洗」 | 状态同步 |
| 洗好挂回（每周） | 家里 | 扫衣架 → 「归柜」 | 状态同步 |
| 换季收纳（每年 2–4 次） | 家里 | 批量扫码 → 「收纳」 | 状态迁移 |
| 想卖 / 想捐（不定期） | 家里 | 扫码 → 「出售」 | 断舍离 |

### 3.6 关键用户旅程（首次 40 分钟，必须顺畅）

```
① 注册登录
② 看到「开始建档·3 秒一件」 → 不做任何复杂设置
③ 拍第一件衣服 → AI 返回 {类别: 卫衣, 主色: 灰, 图案: 纯色, 季节: 春秋, 版型: 宽松}
④ 界面高亮可编辑字段，不确定的字段显示「不确定」而非瞎猜
⑤ 用户点「确认入柜」→ 卡片出现在衣柜列表
⑥ 重复 5–10 件（必须有「接着拍」按钮，不要每次回首页）
⑦ 进标签页，勾选全部 → 生成二维码 → 点「打印」（浏览器打印，A4，可裁剪）
⑧ 剪裁、贴衣架
⑨ 第二天：手机相机扫 → 点「今天穿了」→ 看到本月穿着次数 +1
    ↑ 这一刻决定用户是否留下
```

**设计红线**：
1. ③–⑥ 之间**不能出现任何强制填写的必填项**（价格、购买日期、材质一律可后补）。
2. ⑨ 的扫码页**不能要求登录**（见 §6.3），否则每一次扫码都会撞上登录墙，闭环断裂。

## 4. 价值主张与差异化

### 4.1 竞品盘点与本产品的差异

| 竞品类型 | 代表产品 | 他们做得好 | 他们没做的（我们的机会） |
| --- | --- | --- | --- |
| AI 数字衣柜 App | Ovylo、Dayclo、Lookora、Closet DJ、Wheron | 拍照录入、分类、搭配推荐、穿着次数、CPW、洗衣状态 | **数据输入仍靠手动点击，与物理衣物之间没有连接** |
| 衣物护理识别 | LaundryMax | AI 识别护理标签 + 洗衣分拣 | 只解决「怎么洗」，不管衣物的全生命周期 |
| 二手交易平台 | 闲鱼、多抓鱼 | 交易流量 | 不管「哪些该卖」，决策环节空白 |
| 衣橱整理服务 | 线下整理师 | 有仪式感、有效果 | 一次性服务，无法持续维护 |

**结论：红海里所有人都在做「如何管理得更聪明」，没有人做「如何让数据自己流进来」。**

### 4.2 差异化定位图

```
                    ↑ 与物理世界的连接强度
                    │
        【衣橱镜像】  │  ★ 我们的位置
     物理标签+扫码闭环 │
                    │        · NFC 方案（成本高、门槛高）
────────────────────┼────────────────────→ 数据洞察深度
                    │
   · 纯记录型 App     │  · AI 搭配推荐类 App
  （只用清单，无洞察） │  （推荐做得深，但输入数据不可靠）
```

**我们同时向左上（物理连接）和右下（洞察深度）延伸，而这两者互为因果：连接带来真实数据，真实数据带来可信洞察。**

### 4.3 为什么这个位置不容易被抄

1. **它需要用户做一次有心理门槛的动作**（给衣服贴标签），成熟大厂倾向于砍掉这种门槛，因此很难跟进；
2. **它绑定的是硬件式心智**（标签 + 扫码），一旦贴满一整个衣柜，迁移成本极高；
3. **数据资产随时间增值**：用了半年的衣柜，其历史穿着记录无法被新 App 复制。

## 5. AI 在产品中的角色（v2.0 收敛为「1 + 1」）

### 5.1 一个产品级 AI + 一个实验级 AI

| # | 定位 | 触点 | 输入 | 输出 | 解决什么 |
| --- | --- | --- | --- | --- | --- |
| **AI ①** | **产品功能（做透）** | **衣物自动建档** | 衣服照片 | 类别、主色、图案、季节、版型、风格（材质仅建议） | 把「填 12 个字段」变成「改 2 个字段」 |
| **AI ②** | **离线实验（不做进界面）** | 水洗标识别 | 水洗标照片 | 材质、洗涤温度、漂白、烘干、熨烫、干洗 | 证明 AI 能力边界探索与 Prompt 迭代方法论 |
| ~~AI ③~~ | ~~衣柜分析~~ | — | — | — | **v2.0 砍掉**：数据量不够，且结构化统计用 SQL 就能算 |

### 5.2 为什么「只做一个 AI 功能」不削弱比赛表现

这是 v2.0 最重要的一条判断，值得单独说清：

> **本次赛题要求的 AI 能力，主要落在「使用 AI 完成核心闭环 + 记录关键 Prompt 与迭代过程」上，而不是「产品里 AI 功能的数量」。**

也就是说，你的 AIGC 叙事由三部分构成：

| 叙事部分 | 由什么支撑 | 成本 |
| --- | --- | --- |
| **产品里有一个真实必要的 AI** | 衣物自动建档（一个场景做透） | 3–4 天 |
| **开发过程本身是 AI 工程化实践** | `AGENTS.md`、`skills/`、Prompt 版本管理、Feature Workflow、`AI-USAGE-LOG` | 分散每日 5–30 分钟 |
| **AI 能力有边界、被验证过** | 水洗标实验的 V1→V2 对比 + 衣物识别 20 件测试集 | 1–2 天 |

**三个 AI 功能各做到 60%，远不如一个做到 95% + 一份能自证的过程记录。**

### 5.3 为什么衣物建档这个 AI 是「必要的」而不是「硬塞的」

- 录入是产品的第一道生死关。如果建档要用户手填 12 个字段，产品直接死在第一次使用（对应 P1）。
- 而且这个场景的 AI 收益**可被量化**：字段数从 12 → 2，单件耗时从 60 秒 → 10 秒。这是能在答辩里报出数字的地方。

### 5.4 AI 使用原则（写入开发规范，不可违背）

1. **AI 永远不直接写最终数据。** AI 只输出「建议」，用户在界面上确认/修改后才落库（Human-in-the-loop）。
2. **不允许猜测无法从图片可靠判断的属性。** 颜色、图案、类别可以判；**材质只能给「建议」；品牌一律不猜**；判断不准的字段必须输出 `uncertain`，而不是编造。
3. **结构化输出。** 视觉任务强制返回 JSON Schema，前端据此预填表单，不解析自由文本。
4. **两条识别链路物理隔离。** `Garment Vision`（进产品）与 `Care Label Vision`（离线实验）是两条独立 Prompt、独立脚本、独立样本集。
5. **能力边界透明。** 界面明确标注「AI 识别结果仅供参考，请确认后保存」。
6. **AI 失败必须可降级。** 接口超时/报错时，用户仍能手动填表完成建档 —— 这条是硬性验收项。

### 5.5 AI 识别输出示例（衣物建档）

```json
{
  "category": "衬衫",
  "primaryColor": "浅蓝色",
  "pattern": "纯色",
  "fit": "宽松",
  "season": ["春", "秋"],
  "style": "通勤",
  "material": "uncertain",
  "brand": "uncertain",
  "confidence": {
    "category": 0.95,
    "primaryColor": 0.91,
    "pattern": 0.96,
    "fit": 0.78
  }
}
```

### 6.1 MVP 功能树（收缩后，只保留这些）

### 6.2 坚决不做清单（v2.0 扩充版）

| 功能 | 舍弃理由 |
| --- | --- |
| AI 搭配推荐 / 每日穿搭 | 红海标准功能，不是差异化；需要高质量风格数据才能做好 |
| 天气接入与天气推荐 | 同上，锦上添花，会把开发节奏带偏 |
| 社区 / 穿搭广场 / 关注体系 | 需要运营和内容冷启动，对比赛项目是纯负担 |
| 二手平台（闲鱼等）对接 / 担保交易 | 涉及资质、资金与合规，且不是核心价值 |
| NFC 标签 | 成本高、手机兼容性差异大、Demo 风险高 |
| 多人共享衣柜 / 家庭账号 | 数据模型复杂度上升，**MVP 连 Wardrobe 表都不建** |
| 全自动衣柜盘点（摄像头阵列） | 硬件成本与工程复杂度远超范围 |
| **A4 三种标签规格（30×20 / 50×30 / 70×40）** | **分页、裁切线、混排的边界情况能吃掉 2–3 天，收益极低** |
| **PDF 生成（`@react-pdf` / Puppeteer）** | **浏览器 `Ctrl+P` 打印出来的纸一模一样，工作量从 2.5 天降到 0.5 天** |
| **10 种生命周期状态** | **10 个状态 = 10 套 UI 分支、10 个图标、10 种校验提示；演示只用 5 个** |
| **独立统计页（利用率 / 闲置清单 / 重复购买 / 最近穿着）** | **演示镜头只需要「本月穿着次数 +1」这一个数字** |
| **衣物列表四维筛选（类别+颜色+季节+状态）** | **筛选 UI 很吃时间，留「类别」+ 搜索足够** |
| **水洗标识别做进产品界面** | **降级为离线实验，保留 90% 叙事价值，省 2 天开发** |
| **自研扫码器（ZXing）** | **手机系统相机自带扫码，识别这一段代码量为 0** |
| 对象存储（OSS/MinIO）、Docker、Playwright E2E、Zod 全量校验 | 「看起来专业」的基建，对评分贡献 ≈ 0 |

**决策纪律：任何新功能提案，必须回答「它解决 P1–P5 中的哪一个」，答不上来的一律不做。并且必须回答「为它删掉哪个现有功能」。**

### 6.3 一个关键的产品设计决定：扫码页免登录（能力型 URL）

这是 v2.0 新增的、也是**最容易被忽略但决定 Demo 成败**的一条。

**问题**：用户站在衣柜前，用**手机系统相机**扫衣架上的二维码 → 系统打开一个**全新的浏览器标签页**。这个标签页里没有登录 Cookie。

如果 `/g/{token}` 要求登录，实际流程会变成：

```
扫码 → 打开页面 → 跳登录页 → 输账号密码 → 再跳回 → 点「穿了」
```

**这个产品就死了。** 真实用户不会用，答辩演示也会卡住。

**方案**：把 `/g/{token}` 设计成**能力型 URL（capability URL）**。

| 设计点 | 说明 |
| --- | --- |
| **不需要登录** | token 本身就是凭证，谁拿到这个链接，谁就能操作这一件衣服 |
| **只显示最小信息** | 名称、缩略图、状态 + 6 个动作按钮。不显示其他衣物、不显示统计、不显示账号信息 |
| **token 规格** | 10–12 位 base62 随机串（空间约 10¹⁸，不可遍历）。**禁止用自增 ID 或可预测短码** |
| **权限范围** | 只授予「这一件衣服的有限动作」，不授予账号权限 |
| **演示收益** | **现场可以让评委用自己的手机扫，立刻可用** —— 这个效果远强于你自己演示 |
| **后续加固（不在 MVP）** | 敏感动作（出售/淘汰）要求登录；标签上印可见编号做二次确认 |

**安全边界的诚实说明**（写进 `docs/ARCHITECTURE.md`，答辩主动讲，是加分项）：

> 「扫码页采用 capability URL 设计，免登录是刻意的产品决策 —— 物理标签本身就贴在用户家里，属于私域凭证。token 为 12 位随机串不可遍历，且只授予单件衣物的有限动作。我们接受『拿到链接即可操作』的风险模型，并在后续版本中对出售等敏感动作增加二次确认。」

## 7. 成功度量

### 7.1 衡量产品是否成立的指标

| 指标 | 定义 | 目标 | 说明 |
| --- | --- | --- | --- |
| **建档完成率** | 首次登录后完成 ≥5 件衣物建档的用户占比 | ≥ 70% | 验证假设 B |
| **建档速度** | 单件从拍照到确认的耗时 | ≤ 10 秒 | 验证 P1 |
| **标签打印率** | 建档后实际打印出标签的用户占比 | ≥ 50% | **验证假设 A 的关键行为指标** |
| **扫码成功率** | 打印的标签中，能被手机相机成功扫开的比例 | **100%** | **硬指标，不达标不能进入演示** |
| **扫码活跃度** | 打印标签的用户中，7 日内至少扫码 1 次的比例 | ≥ 60% | **生死指标** |
| **AI 字段采纳率** | 用户未修改直接确认的 AI 字段占比 | ≥ 75% | 验证 AI 识别质量是否够用 |

> **北极星指标：连续 4 周保持扫码记录的用户数。**
> 理由：它同时涵盖「建档成功」「贴了标签」「愿意扫码」「数据有积累」四个环节，是唯一能证明这个产品真的在现实世界中被使用的指标。

> **v2.0 说明**：指标只保留 6 个，全部与「录入 + 扫码」这条主轴相关。原 v1.0 的「数据完整度」等指标在 4 周内无法验证，予以删除。

### 7.2 比赛叙事（答辩稿用）

> 我们最初以为用户需要「更聪明的穿搭推荐」；访谈后发现，真正的问题不是不会搭配，而是**数字衣柜无法低成本获得真实穿着数据**。
> 因此我们设计了连接现实衣柜与数字档案的衣物标签系统：二维码编码与解码属于确定性任务，交给手机系统相机与传统库；衣物属性识别属于语义任务，交给多模态模型；AI 输出存在幻觉风险，因此一律经用户确认后入库；Prompt 通过 20 件衣物的固定测试集完成两轮 Eval 迭代。
> 我们主动放弃了 AI 搭配、多规格标签、多维筛选等功能 —— 因为四周内它们不解决核心假设，只会稀释完成度。

### 7.3 社会价值（放在结尾，不强行上价值）

- 减少冲动消费与衣物浪费；
- 让「闲置衣物」进入出售 / 捐赠渠道，而不是垃圾桶；
- 用 Cost Per Wear 让消费者看见「便宜的衣服可能最贵」。
