## 1. 开发原则

### 1.1 最重要的结构改动：从「水平分层」改为「垂直切片」

v1.0 的排法是先做完所有 CRUD、再叠 QR、再叠扫码 —— **问题是到第 8 周才第一次知道扫码能不能跑通**，而扫码恰恰是最容易出问题的环节（打印尺寸、纸张反光、手机浏览器、HTTPS、URL 编码）。一旦第 8 周翻车，已经没有时间回头。

v2.0 改成：

> **第 6 周结束前，做一根最薄的垂直切片：**
>
> ```
> 拍 1 张照片 → AI 返回 JSON → 存进数据库 → 列表里出现这件衣服
>      → 给它生成一个二维码 → 打印出来 → 手机相机扫开
>      → 点「穿了」→ 状态变了
> ```
>
> 页面可以丑、只有 1 个字段、没有登录（用户写死）。**但这根针必须扎穿。**

扎穿之后，剩下三周只是「加宽」，而不是「从零开始赌」。**这是 4 周项目唯一靠谱的排法。**

### 1.2 六条铁律

1. **不学新框架。** 熟悉 Vue 就用 Vue，熟悉 React 就用 React。绝不为了比赛现学 Next.js。
2. **不做清单外的功能。** 每个功能提案必须回答「它解决 P1–P5 中的哪一个」，且必须回答「为它删掉哪个现有功能」。
3. **AI 永远不直接写最终数据。** AI 只出「建议」，用户确认后才落库。
4. **确定性任务用传统算法，语义任务才交给 AI。** 二维码编码用库、解码交给手机系统相机，**不包装成 AI**。
5. **所有关键 Prompt 进 Git。** `prompts/` 下的每次修改都可回溯。
6. **页面数上限 8 个。** 见产品文档 §6.1。新增一页必须删掉一页。

### 1.3 学习预算：每个知识点最多 2 小时，然后必须动手

| 知识点 | 学习时长 | 立刻产出 |
| --- | --- | --- |
| 多模态 / Vision API | 1h | 2h 写完 PoC |
| Structured Output | 1h | 2h 定义 Schema 并跑通 |
| Skill | 0.5h | 1h 写第一个 SKILL.md |
| Agent 工程化 | 1h | 2h 跑通一次 Feature Workflow |
| Eval | 0.5h | 2h 建 20 件测试集 |

### 1.4 明确「本次不学」清单

**C 级（坚决不碰）**：LangChain、LangGraph、向量数据库、RAG、MCP Server 开发、多 Agent 框架、模型微调、自训练 CV 模型、Kubernetes。

## 3. 技术方案（v2.0 大幅简化）

### 3.1 技术栈

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 前端 + 后端 | **Next.js + TypeScript**（或 Vue 3 + Vite + Express） | **选你最熟的**。单体应用，不拆服务 |
| UI | Tailwind CSS（或 Element Plus） | 不手写设计系统 |
| 数据库 | **PostgreSQL**（或 MySQL） | 关系型足够 |
| ORM | **Prisma** | Schema 即文档 |
| 鉴权 | 简单 session / JWT | 邮箱 + 密码，**不做邮箱验证、不做找回密码、不做第三方登录** |
| 图片存储 | **本地磁盘** `public/uploads` | **不上对象存储**。注意纳入备份 |
| 二维码生成 | `qrcode`（npm，5 行代码） | 服务端生成 PNG |
| 二维码识别 | **无** | **手机系统相机自带，代码量为 0** |
| 标签打印 | **HTML + CSS `@page` + 浏览器 `Ctrl+P`** | **不引 PDF 库**，见附录 B |
| 多模态模型 | 任一支持图片输入 + JSON 输出的 LLM API | 抽一层 adapter，便于更换 |
| 部署 | **VPS + Node + pm2 + Nginx + HTTPS** | **不要求 Docker**（熟就用，不熟就别花时间） |
| 测试 | 少量单测（Vitest）+ 手工 E2E | **不上 Playwright** |
| 校验 | 手写必要校验 | **不上 Zod 全量校验** |

## 4. 数据模型（v2.0 简化）

### 4.1 只有 4 张表

```
User 1──n Garment 1──n GarmentEvent
                  │  1──1 Label
```

### 4.2 Schema

```prisma
model User {
  id        String   @id @default(cuid())
  email     String   @unique
  password  String            // bcrypt hash
  createdAt DateTime @default(now())
  garments  Garment[]
}

model Garment {
  id             String   @id @default(cuid())
  userId         String
  name           String            // 「灰色圆领卫衣」，AI 生成，用户可改
  category       String            // 衬衫 / 卫衣 / 长裤 ...
  primaryColor   String?
  pattern        String?           // 纯色 / 条纹 / 格纹 / 印花
  fit            String?           // 修身 / 常规 / 宽松 / oversize
  style          String?
  material       String?           // 仅建议值，可为空
  brand          String?           // 不猜，仅用户填
  season         String?           // "春,秋"
  price          Decimal?          // 可空，允许后补
  purchasedAt    DateTime?         // 可空
  photoUrl       String?
  status         GarmentStatus @default(IN_CLOSET)
  aiConfidence   Json?             // 存原始置信度，便于 Eval 分析
  createdAt      DateTime @default(now())
  events         GarmentEvent[]
  label          Label?
}

enum GarmentStatus {
  IN_CLOSET    // 在柜
  WORN         // 穿着中
  TO_WASH      // 待洗（含干洗中）
  STORED       // 季节收纳
  RETIRED      // 已退出（出售 / 捐赠 / 淘汰）
}

model GarmentEvent {
  id         String   @id @default(cuid())
  garmentId  String
  type       EventType
  source     String   @default("manual")   // "scan" | "manual"
  createdAt  DateTime @default(now())
}

enum EventType {
  WORN          // 今天穿了
  WASHED        // 洗了
  DRY_CLEANED   // 送干洗
  RETURNED      // 归柜（洗好/干洗取回）
  STORED        // 收纳
  SOLD          // 出售/捐赠/淘汰
}

model Label {
  id        String    @id @default(cuid())
  garmentId String    @unique
  token     String    @unique          // 12 位 base62，二维码内容 = /g/{token}
  code      String    @unique          // 人类可读编号，如 G018（标签上同时印出来，兜底用）
  printedAt DateTime?
  createdAt DateTime  @default(now())
}
```

### 4.3 状态映射（不做白名单校验，只做一张映射表）

v2.0 **删掉了 v1.0 的白名单状态迁移校验** —— 那是很好的工程实践，但 4 周内的投入产出比不成立。改为一张纯映射表：

| 事件 | → status | 说明 |
| --- | --- | --- |
| `WORN` | `WORN` | 今天穿了 |
| `WASHED` | `TO_WASH` | 洗了（含机洗/手洗） |
| `DRY_CLEANED` | `TO_WASH` | 送干洗 |
| `RETURNED` | `IN_CLOSET` | 归柜 |
| `STORED` | `STORED` | 季节收纳 |
| `SOLD` | `RETIRED` | 出售/捐赠/淘汰 |

```
      ┌────────────┐  WORN    ┌──────────┐
      │  IN_CLOSET │─────────▶│   WORN   │
      │   在柜      │◀─────────│  穿着中   │
      └────────────┘ RETURNED └────┬─────┘
          ▲    ▲                    │ WASHED / DRY_CLEANED
          │    │                    ▼
          │    │              ┌──────────┐
          │    └──RETURNED────│ TO_WASH  │
          │                   │  待洗     │
          │                   └──────────┘
          │
      ┌───┴────┐   STORED   ┌──────────┐
      │ STORED │◀───────────│ 任意状态  │
      │ 已收纳  │            └──────────┘
      └────────┘
                     SOLD
          任意状态 ──────────▶ RETIRED 已退出
```

**实现要点**：`POST /api/events` 写一条 `GarmentEvent`，同时用映射表更新 `Garment.status`。**每次操作都留痕，这是「数据沉淀」和详情页时间线的数据来源。** v1.0 的 `WearRecord` + `CareRecord` 两套表合并成这一张。

### 4.4 API 清单（9 个）

| 方法 | 路径 | 鉴权 | 说明 |
| --- | --- | --- | --- |
| POST | `/api/auth/register` `/api/auth/login` | 否 | 最简账号 |
| GET | `/api/garments` | 是 | 列表；`?category=` + `?q=` 搜索 |
| POST | `/api/garments` | 是 | 新建（携带已确认的 AI 字段） |
| GET/PATCH/DELETE | `/api/garments/:id` | 是 | 详情 / 修改 / 删除 |
| POST | `/api/vision/garment` | 是 | 图片 → 衣物属性 JSON（**不落库**） |
| GET | `/api/labels?ids=` | 是 | 批量为选中衣物生成/取回 label + token |
| POST | `/api/events` | 是 | 详情页手动改状态 |
| **POST** | **`/api/g/:token/action`** | **否（token 即凭证）** | **扫码页动作：`{action:"worn"\|"washed"\|"dry_cleaned"\|"returned"\|"stored"\|"sold"}`** |
| GET | `/api/stats` | 是 | 本月穿着次数 / 在柜件数 / 平均 CPW |

**约束**：`/api/vision/garment` **只返回建议，绝不写数据库**。落库统一由用户确认后的 `POST /api/garments` 完成 —— 这是 Human-in-the-loop 在接口层的体现，也是验收项。

## 7. AI 工程规范

### 7.1 Prompt 版本管理

- 所有 Prompt 以文件进 `prompts/`，命名 `{task}-v{n}.md`
- 每次修改必须：改版本号 + 文件头写 `## 变更原因` + `docs/AI-USAGE-LOG.md` 记一条
- 禁止在代码里硬编码长 Prompt
- 每个 Prompt 文件含：用途、输入约束、输出 Schema、已知失败模式、对应 Eval 结果

### 7.2 Structured Output 约定

- 视觉任务一律返回 JSON，字段名与数据库字段一致，减少映射层
- 必带 `confidence` 对象；**低于 0.7 的字段不预填 / 标黄提示**
- 禁止返回自由文本让前端正则解析
- 服务端做**必要的 Schema 校验**（手写即可，不上 Zod 全量）；校验失败重试一次，再失败返回 `AI_UNAVAILABLE`，前端降级为手动填表

### 7.3 Skill 清单（v2.0 只写 3 个）

| Skill | 作用 |
| --- | --- |
| `skills/garment-ai/SKILL.md` | 改识别功能前先读 schema；颜色可判、材质只建议、品牌不猜；不确定输出 `uncertain`；改 API 必跑测试 |
| `skills/code-review/SKILL.md` | Review 检查项：错误处理、降级路径、边界、token 权限、是否有测试 |
| `skills/testing/SKILL.md` | 边界用例生成策略（空态、超长、超大文件、非法 token、重复提交） |

> `AGENTS.md` 与 Skills 要**保持针对性**，不要越写越臃肿。目标是约束，不是堆砌。

第 6 周 → 扎穿一根针
         拍照 → AI → 落库 → 列表 → 二维码 → 手机扫开 → 状态变
         （丑没关系，必须通）

第 7 周 → 加宽到能用的衣柜
         注册 → 建档 10 件 → 列表 → 详情 → 时间线 → CPW

第 8 周 → 把现实衣架接进数据库
         打印 50×30 标签 → 贴衣架 → 扫码 → 数据条 +1 → 上线

第 9 周 → 只做证据，不做功能
         20 件 Eval / 8 张水洗标 / 3 人试用 / 彩排

第 10–11 周 → 冻结，只修 Bug
         文档 / PPT / 视频 / 答辩

铁律：
  ① 不学新框架        ② 不做清单外功能
  ③ AI 只建议，人确认   ④ 二维码不是 AI
  ⑤ Prompt 进 Git     ⑥ 页面数上限 8 个
  ⑦ 落后就砍功能，不砍证据
```

**砍减的三条判断标准**（后续若要再砍，按此顺序）：

1. **它对「扫码闭环」这个核心假设有没有贡献？** 没有 → 优先砍。
2. **它的工作量 / 叙事价值比是多少？** 比值高（如 A4 多规格 PDF）→ 优先砍。
3. **砍了之后演示会不会变差？** 不会 → 砍。会（如实物打印）→ 保留。

## 附录 B：标签打印方案（核心技术细节）

用 HTML + CSS 打印替代 PDF 生成库。**打印出来的纸与 PDF 方案完全一致，代码量降到 1/10。**

```css
/* 关键：声明纸张为 A4，并去掉浏览器默认边距 */
@page {
  size: A4;
  margin: 8mm;
}

.sheet {
  display: grid;
  /* A4 可用宽 194mm；50mm × 3 列 + 2mm 间距 × 2 = 154mm */
  grid-template-columns: repeat(3, 50mm);
  /* 可用高 281mm；30mm × 8 行 + 2mm 间距 × 7 = 254mm */
  grid-auto-rows: 30mm;
  gap: 2mm;
}

.label {
  width: 50mm;
  height: 30mm;
  border: 1px dashed #bbb;   /* 裁切参考线，打印后可剪 */
  box-sizing: border-box;
  display: flex;
  align-items: center;
  gap: 3mm;
  padding: 2mm;
  break-inside: avoid;       /* 防止标签被分页拆开 */
  print-color-adjust: exact; /* 保证二维码黑白不被浏览器"节省墨水"处理掉 */
}

.label img.qr {
  width: 24mm;
  height: 24mm;
}

@media print {
  .no-print { display: none; }  /* 隐藏页面上的「打印」按钮和说明 */
}
```

**排版容量**：**24 张 / A4 页**（3 列 × 8 行）。

**打印时必须提醒用户的设置**（写在页面上，一行字就够）：

> 缩放 **100%** · 关闭「页眉和页脚」· 勾选「背景图形」

**为什么选 50×30mm 而不是 30×20mm**：
标签越小，二维码越小，手机相机能稳定扫到的距离越短。**为了省一张纸而牺牲「能不能扫」，是方向性错误。** 50×30mm 在 20–30cm 距离内可稳定识别。

**标签上必须同时印人类可读编号**（如 `G018`）：二维码被磨花、被遮挡、或扫码失败时，用户还能手动输入编号。这是**零成本的兜底设计**。

## 附录 C：演示脚本（4 镜头）

| 镜头 | 内容 | 时长 | 说明 |
| --- | --- | --- | --- |
| **1** | 打开现实衣柜，镜头扫过一排贴着标签的衣架 | 5s | 建立「物理世界」的真实感 |
| **2** | 手机**系统相机**对准衣架上的二维码 → 自动弹出链接 → 点开 | 5s | **重点展示没有装任何 App，也没有登录** |
| **3** | 页面点「今天穿了」→ 「已记录 ✓」 | 3s | 交互闭环 |
| **4** | 电脑（或手机）首页：**本月穿着次数 +1** | 5s | 数字增长的即时反馈 |

**为什么这个顺序有效**：它把「物理动作」和「数字变化」放在同一段 18 秒里，观众能直接理解产品在做什么 —— 这比解释「我们用了多模态模型」直观一百倍。

**彩排要点：**
- 镜头 2 必须拍到「相机 → 链接弹出」那一帧，否则观众会以为你在用某个扫码 App
- 提前把演示手机的浏览器标签清理干净，避免露出其他网站
- 网络方案：优先用演示手机自己的流量，而不是现场 WiFi（现场 WiFi 经常是最不可靠的一环）

## 附：最终能力目标（自检用）

项目结束时，你应该能这样解释技术选择：

> 「衣物属性识别属于语义任务，我们用多模态模型并强制 Structured Output；
> 二维码的编码用成熟库、解码交给手机系统相机 —— 这属于确定性任务，不需要 AI；
> AI 输出存在幻觉风险，因此引入 Human-in-the-loop，AI 只出建议、用户确认后才落库；
> 材质与品牌这类无法从图片可靠判断的属性，我们要求模型输出 `uncertain` 而不是猜测；
> Prompt 通过 20 件衣物的固定测试集完成了两轮 Eval 迭代，另有水洗标识别的独立实验验证了能力边界；
> 开发阶段用可复用的 Skills 规范 Coding Agent 的实现、Review 与测试；
> 我们主动放弃了多规格标签、多维筛选、AI 搭配等功能 —— 因为四周内它们不解决核心假设，只会稀释完成度。」

这段话的信息量，远大于「我们使用了先进的多 Agent 协同框架」。
